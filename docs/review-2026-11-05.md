# 代码审查 · 性能热点 · 开源对照

对象：`LineOcrSearch`（Win32 + ONNX OCR 取词 + 本地文档全文搜索，单 exe 17.4MB）
时间：2026-11-05 · 基线 `4ba63e7`

> **落地状态（2026-11-05 晚更新）**：B1/B2/B3/B4/B5/B6/B7/B8/B11、P1 缓存版本、
> P2 锁外 I/O、P3 免分配行匹配、**P2 单库缓存** 均已实现并有测试覆盖。
> 未做：P4 XML 零拷贝、B9 DPI、B12 页眉页脚。
> 单库缓存后的实测（2000 个 2KB 文本文件）：冷 109ms / 热 15–16ms（改前 532ms / 500ms，再往前每文件一个缓存文件时 1234ms）。
> 44 份 doc 真实语料：冷 62ms / 热 15ms，命中 463 条不变。

---

## 一、结论摘要

1. **没有内存安全级别的严重漏洞**。CFB / ZIP / inflate / BIFF 这些攻击面都做了边界与环检测（`tests/test_legacy.cpp` 里那几组脏数据用例是对的），自实现解析的质量高于同类个人项目。
2. **确定性 Bug 有 3 个值得马上修**：`Tab` 在搜索框被 RichEdit 吃掉（已实测复现）、搜索线程直接读 `g.settings`（跨线程数据竞争）、取词失败后每 1.2 秒无限重试（空转 CPU）。
3. **真正的性能天花板是"每次搜索全目录重扫 + 每文件一个缓存文件"**：44 份 doc 只要 78ms，但 2000 个文本文件要 **1.2 秒**（冷 1234ms / 热 1188ms，缓存几乎无收益）。按 `kMaxScanned = 20000` 推算上限约 **12 秒/次**，这是它和 DocFetcher/Recoll 的分水岭。
4. **架构上是"无索引 + 文本缓存"路线**，与 ripgrep-all（rga）最像；与 DocFetcher / Recoll 的倒排索引路线不同。当前选择对"几千份文档、随改随搜"是合理的，代价是文件数一多就线性劣化。
5. **取词链路（原生 EDIT 精确坐标 → UIA 对齐 → OCR 兜底）比开源同类更精细**：Text-Grab / PowerToys 是 UIA 拿到整块文本就完事，没有"把 OCR 的每字像素位置对齐到 UIA 原文"这一步。

## 二、Bug 清单（按严重度）

### B1 · 中 · Tab 在搜索框里被当成制表符，焦点链断掉（已实测）

`README.md` 写着「`Tab` / `Shift+Tab`：输入框 → 搜索 → 设置 → 结果列表 循环」，但 `MainProc` 的 `WM_KEYDOWN` 只在消息被派发到主窗口时才执行 `CycleFocus()`（`src/main.cpp:862+`）。焦点在 RichEdit 上时，按键消息只会进 `EditSubclass`（`src/main.cpp:246`），而它只拦了 `VK_RETURN` / `VK_DOWN` / `VK_UP` / `Ctrl+F`，`Tab` 落到 `DefSubclassProc` → RichEdit 是 `ES_MULTILINE`（`CreateControls` 里强制加的），直接把 `\t` 插进关键词。

实测（`tests/tmp/uitest4.cpp`，投递真实消息序列）：

```
WM_GETTEXTLENGTH=3        # 先塞入 "abc"
[after Tab] focus=RICHEDIT50W（没变）
edit after Tab: WM_GETTEXTLENGTH=4   # 多了 1 个字符 = 制表符
```

影响：Tab 不起作用，且关键词里混入不可见字符 —— 因为 `RunSearch` 按空格/`\t` 切关键词，`abc\t` 会被当成两个词做 AND，搜索结果莫名其妙变少。

修法（`EditSubclass` 里加 4 行）：

```cpp
if (m == WM_KEYDOWN && wp == VK_TAB) {
    PostMessageW(g_hwndMain, WM_KEYDOWN, VK_TAB,
                 (GetKeyState(VK_SHIFT) & 0x8000) ? 1 : 0);
    return 0;                      // 吃掉，别让 RichEdit 插 \t
}
```

### B2 · 中 · 搜索线程直接读 `g.settings`，跨线程数据竞争

`SearchThreadProc` 在工作线程里读全局：

```cpp
req.rootDir      = g.settings.rootDir;        // src/main.cpp:164
req.searchOffice = g.settings.searchOffice;
```

而主线程会在 `WM_COMMAND`（保存设置）和 `WM_DROPFILES`（拖新文件夹）里直接改 `g.settings`，`ShowSettingsDialog(hwnd, g.settings, ...)` 甚至是**按引用边开边改**。`std::wstring` 的赋值不是原子的：搜索线程正在 `req.rootDir = ...` 拷贝时主线程改 `rootDir`，可能出现读半截缓冲区 → 路径乱码（表现为"搜不到"）甚至偶发崩溃。

取词那条链路已经做对了（`CaptureResultMsg.settings` 是快照），搜索这条漏了。修法：`StartSearch` 里在**主线程**填好 `SearchRequest` 再传进线程，线程不再碰 `g`。

### B3 · 中 · 取词失败后每 1.2 秒无限重试

```cpp
if (g_fired && (DWORD)(now - g_lastAttempt) < 1200) return;   // src/main.cpp:604
```

`g_fired` 只在鼠标移动时清零。所以鼠标停在一片没有文字的区域（桌面、图片、按钮）时，每 1.2 秒就会：截屏两次（80px、150px 两圈）→ 跑 OCR → 失败 → 再来。每次约 40–100ms CPU，占空比 5–8%，而且 `SetLeftStatus("未取到文字…")` 还会一直刷状态栏。

修法：同一个点失败 N（3）次后置 `g_gaveUp = true`，只在鼠标移动时恢复；或者失败按指数退避到 10 秒。

### B4 · 中 · docx 表格单元格之间没有分隔符，会造成跨列误命中

`ExtractWordXml`（`src/office.cpp:354`）只处理 `t/p/tab/br/cr`，`<w:tc>`（单元格）没加分隔。一行三列 `闭塞` `区段` `办理` 抽出来是 `闭塞区段办理`，搜"区段办"会命中一个原文根本没有的词。

同类问题：`<w:delText>`（修订模式下被删除的文字）被整段丢弃 —— 想搜"修订前版本里的说法"就搜不到。这两点都会影响"和 Word 里 Ctrl+F 的结果对不上"的信任度。

修法：`name == "tc"` 且是闭合标签时 `out += L'\t'`；`delText` 按 `t` 一样处理（或做成设置项）。

### B5 · 中 · xlsx 两处静默丢数据

- 单元格类型只认字面量 `t="s"`（`src/office.cpp:462` 的 `tag.find("t=\"s\"")`）。单引号 `t='s'`、等号两侧有空格、或者属性顺序变体都会判不出共享字符串，于是把**共享字符串索引当数字输出**（本该是"闭塞"，结果显示"37"）。
- `legacy_office.cpp:481`：单表超过 20 万个单元格直接 `return`，`sheet.full = true` 但**没人读这个标志**。用户看到的是"这个大表搜不到后面几万行"，且没有任何提示。

修法：类型解析改成解析属性名值对；超限时在正文里插一行 `【表格过大，已截断】`，并计入状态栏提示。

### B6 · 低 · `.doc` 的压缩片段一律按 CP1252 解码

`legacy_office.cpp:296`：`MultiByteToWideChar(1252, ...)`。Word 的 `fCompressed` 表示"每字符 1 字节"，规范上按 CP1252 解释；但中文版 Word 生成的片段里如果出现 GBK 双字节（部分第三方工具生成的 doc 会这样），会被拆成两个西欧字符，中文搜索必然落空。

修法：按 FIB 里的 `lid`（语言 ID）选代码页，中文用 936，失败再退回 1252。

### B7 · 低 · 单个坏分片就让整篇抽取失败

`ExtractDocText` 里 `if (fc + take > doc.size()) return false;`（`legacy_office.cpp:294/303`）——一块 piece 越界就把整份文档判死；`xlsx` 里某个 sheet 解压失败也是 `continue`（这个还好）。建议改为"跳过该段，继续后面的 piece"，末尾若 `out` 为空才返回 false。

### B8 · 低 · 超长路径的缓存永远失效

`ReadDiskHeader`（`src/cache.cpp:182`）只读 8KB 找头行，超过 8KB 的 key 直接判失效。路径超过约 2700 个汉字（`\\?\` 长路径）时，每次搜索都会重建缓存。极端场景，但改起来便宜（读 64KB，或先读 4 字节长度）。

### B9 · 低 · 没有 `WM_DPICHANGED` 处理

`EnablePerMonitorDpi()` 声明了 PMv2，但 `MainProc` 没有 `WM_DPICHANGED` 分支。窗口从 100% 屏拖到 150% 屏时，字体、`g_lineH`、按钮布局都不重算 → 文字被裁、卡片高度算错（`MeasureItem` 用旧的 `g_lineH`）。多屏混合 DPI 是笔记本外接显示器的常见配置。

### B10 · 低 · `ShowCursor(FALSE)` 用全局计数隐藏光标

`capture.cpp:62`。当前路径安全（`BitBlt` 后立刻 `ShowCursor(TRUE)`，中间没有 early return），但它是进程级计数器：将来谁在这两行之间加一句 `return`，光标就永久消失。建议改成"只在截屏那一帧用 `SetCursor(nullptr)` 或改成 RAII 守卫"。

### B11 · 低 · 「命中 N 条」在超大命中时会偏小

`kMaxCollect = 8000`（`search.cpp:28`）收满即停，`totalHits` 只统计到收集上限为止。状态栏那个数字会被用户当成真实次数（"闭塞 463 条"是对的，但一个目录里命中两万次时会显示 8000）。`truncated` 只在"没有暂存可加载"时才加到状态栏，容易被忽略。建议：`truncated` 时始终显示"≥"。

### B12 · 设计说明（不是 bug）· 为什么和 Word 的 Ctrl+F 差几条

`.doc` 只取 `ccpText` 范围内的正文（`legacy_office.cpp:282`），页眉页脚、脚注、批注、文本框都在 `ccpText` 之后，被有意丢弃。之前《行规》"闭塞"Word 报 177 处、本程序报 171 处，差的就是这部分。如果希望一致，可按 `ccpFtn` / `ccpHdd` 把页眉页脚也抽出来，代价是命中数变多、噪音变大。

## 三、性能热点（含实测）

测试环境：同一台机器，`tests/tmp` 下自建语料；时间取 `GetTickCount` 包裹 `RunSearch`。

| 场景 | 冷（无缓存） | 热（有缓存） |
|---|---|---|
| 44 份 doc（含 10.9MB《技规（高铁）》），搜"闭塞" | 78ms | 63ms |
| 2000 个 2KB 文本文件（8 万行） | **1234ms** | **1188ms** |

结论：**文件数才是瓶颈，不是解析速度**。缓存把 1234ms 降到 1188ms（−4%），说明时间花在"每文件一次系统调用"上，而不是"解析"上。

### P1 · 每次搜索重扫目录 + 每文件一次缓存文件打开（最大热点）

`Walker::Walk` 每次都完整走一遍目录树；每个文件都要过 `CacheGet` → `MakeKey`（UTF-8 转换 + 两次 `to_string` 拼接）→ `CreateFileW` 打开 `<hash>.cache` → 读 32KB 以内 → `FromUtf8` 逐行 → 构造 `vector<wstring>`。

2000 文件 → 2000 次 open/read/close + 20 万次字符串分配 ≈ 1.2s，约 **0.6ms/文件**。按 `kMaxScanned = 20000` 推算 ≈ **12 秒/次**，远超"打字即搜"的体感阈值。这也是杀软实时扫描最容易放大的地方（每次 open 都会被过滤驱动拦一次）。

三种改法，按收益排序：

1. **单文件缓存库**（rga 的做法）：所有文档正文进一个 SQLite（或自制 append-only + mmap 索引），key = path + size + mtime + **解析器版本**。一次 open，顺序读，2000 文件应降到 100ms 级。顺带解决 B8 和"缓存文件碎片化"。
2. **目录级 manifest**：每个目录一个 `index.bin`，记录 `文件名 → (size, mtime, 缓存偏移)`，搜索时先比 manifest，命中才去读正文。
3. **常驻文件索引 + `ReadDirectoryChangesW`**：启动扫一次，之后只处理变更（Recoll 用 inotify/FSEvents 的思路，Windows 对应 `ReadDirectoryChangesW`）。这样重复搜索可以到"毫秒级、接近零 IO"。

### P2 · 缓存锁覆盖了磁盘 I/O

`CacheGet` / `CachePut` 全程持 `CacheGate`（`cache.cpp:299`、`344`），而 `CachePut` 内部 `WriteDisk()` 整文件拼串 + 写盘（`cache.cpp:197`），`CacheEndBatch` 还会扫目录 + 排序做配额。建缓存（设置窗里"生成缓存"）跑在 UI 线程上、每个文件都拿锁写盘，此时用户打字搜索会**排队等锁**，表现为"搜索偶发卡 1–2 秒"。

改法：锁只保护 `g_mem` / `g_lru`，`ReadDisk`/`WriteDisk` 放到锁外（读到的结果再回锁内插入；写盘失败也静默）。这是标准的 cache-aside 结构。

### P3 · 每行两次字符串分配

```cpp
std::wstring lineUpper = UpperW(NormalizeWidth(lines[i]));   // src/search.cpp:244
```

`NormalizeWidth` 拷贝一次、`UpperW` 再拷贝一次，8 万行 = 16 万次分配 + 2 次全量字符转换。实测里这部分约占 10–20%。

改法：预先把关键词按同样规则归一化后，直接用 `CompareStringOrdinal(..., TRUE)` 或手写不分配的大小写不敏感 `find`（中文项目里 99% 的行根本不含关键词，先做一次 `wmemchr` 首字符预筛最划算）。

### P4 · docx/xlsx 的 XML 扫描：每个标签 4 次分配 + 整份双拷贝

`ExtractWordXml` / `ExtractSheetXml`（`office.cpp:354`、`417`）对每个 `<...>` 都做 `tag = xml.substr(...)`、`body`、`name`、`inner`，一个 10MB 的 `document.xml` 有几十万标签 → 上百万次小分配。另外 `office.cpp:556` 把解压结果从 `buf` 又拷成 `std::string xml`，峰值内存 ≈ 解压后大小的 2 倍。

改法：改成 `std::string_view`（C++17）/裸指针+长度扫描，零拷贝；`xml` 直接复用 `buf` 的缓冲区。收益：docx 解析 2–3 倍。

### P5 · 结果很多时，拖窗口会重测全表

`RecalcTotalHeight` 在宽度变化时全量重测（`listview.cpp:180+`，已做"加载更多只测尾巴"的增量优化）。但用户连点 20 次"加载更多"到 2000 条后，一次拖动窗口宽度 = 2000 × 6 行文本测量。建议：`WM_SIZE` 期间只标记 dirty，`WM_EXITSIZEMOVE` 再重测；拖动时按旧高度粗绘。

### P6 · 取词链路本身

每次取词：新建线程 → `CoInitializeEx(MTA)` → 截图（1–2 次 `BitBlt` 400×160/300）→ ONNX 推理 → 可能再走 UIA 读全文 → 对齐。正常耗时 40–100ms（含模型首次加载 200–400ms）。热点不在单次，而在 B3 的"失败无限重试"，以及 UIA 在 Chromium/Electron 上读全文（`GetUiaDocumentText` 有 2 秒缓存，但第一次是几十到几百 ms）。整体可接受。

### P7 · 状态栏 16Hz 重绘

`WM_TIMER`（60ms）里 `UpdateMouseStatus` 每次坐标变化就 `InvalidateRect` 状态栏 → 鼠标移动时每秒 16 次重绘整条状态栏。CPU 占用不高但有可见的闪烁感。可在坐标未变（同一像素）时跳过，或把刷新压到 100ms。

## 四、近似的成熟开源项目

### 4.1 取词 / 屏幕 OCR 这一类

| 项目 | 语言 / 体积 | 触发方式 | 文本来源 | 依赖 | 值得借鉴 |
|---|---|---|---|---|---|
| **Text-Grab**（TheJoeFin，MIT，~4.6k★） | C# / .NET，几十 MB | 全局热键（Win+Shift+F） | **UIA TextPattern 优先**，失败退 `Windows.Media.Ocr` | 系统 OCR 语言包 | 双通道取词的产品化：UI 元素直接读无障碍树"100% 准确"，只有图像才 OCR |
| **PowerToys Text Extractor** | C++ 模块 + C#/WPF 独立进程 | 全局热键 | `Windows.Media.Ocr` | 系统 OCR | 模块与 UI 进程分离、命名事件通信；多屏 Overlay 与 DPI 换算（我们的 B9 就是这块） |
| **Umi-OCR**（hiroi-sora，MIT） | Qt + Python，100MB+ | 热键截图 / 批量 / HTTP API | PaddleOCR + RapidOCR 双引擎 | 自带模型 | 双引擎按场景调度；忽略区域遮罩；HTTP API 让别的程序调用 |
| **Pot**（pot-app，Tauri） | Rust + Web | 划词 / 截图 | 插件化：系统 OCR、Tesseract、Paddle、Rapid、在线 | 插件 | OCR 引擎做成插件，换引擎不改主程序 |
| **Capture2Text / Translumo** | AHK / C# | 热键 / 实时循环 | 纯 OCR（Tesseract 等） | 外部引擎 | 实时循环取词的节流策略 |

**与本项目的差异点（取词侧）**

1. **触发模型不同**：开源同类几乎都是**热键触发**（按下才动作），本程序是**鼠标静止轮询**（停 0.5 秒自动取词）。轮询体验更"无感"，但代价是误触与空转（B3），需要更细的状态机——这也是 Text-Grab 们不做轮询的原因。
2. **取词精度更高**：本程序三级兜底里最难的一段是「OCR 给出每字像素位置 + UIA 给出准确文字 → 用对齐算法把两者缝合」，还能按鼠标位置切出"鼠标右边那一段"。开源同类要么只给 UIA 整块文本（Text-Grab），要么只给 OCR 整行（Capture2Text），没有"鼠标指到哪个词"这一层。
3. **依赖策略相反**：Text-Grab / PowerToys 白嫖系统的 `Windows.Media.Ocr`（零体积、装语言包即可，但中文识别质量一般、不能调参）；本程序内嵌 PaddleOCR 的 rec 模型（17MB，识别质量好、离线可控，但没有检测模型，靠"截一条带"绕开检测）。

### 4.2 文档全文检索这一类

| 项目 | 路线 | 索引 | 文档解析 | 增量 / 缓存 | 体积与部署 |
|---|---|---|---|---|---|
| **DocFetcher** | Java + Lucene | **倒排索引**（首次建库慢，之后毫秒级） | Apache Tika（JVM 全家桶） | 手动/定时增量 | JVM + 运行时，几百 MB |
| **Recoll** | C++ + Xapian | **倒排索引**（BM25 排序） | 外部过滤器（antiword / pdftotext / unzip…） | `inotify` / FSEvents 实时增量，可 cron | 需装一堆 filter 工具，但索引可到千万文档级 |
| **ripgrep-all (rga)** | Rust，包一层 ripgrep | **无索引**，线性扫描 | 适配器调 pandoc / pdftotext / ffmpeg / 内置 zip | **SQLite + zstd 缓存**，key = path + mtime + adapter 版本 | 需 rg + 各转换工具 |
| **本项目** | C++ / Win32 | **无索引**，线性扫描 | **自实现**（inflate + ZIP + XML 扫描 / CFB + BIFF8） | 每文件一个 `.cache` 文本文件 + 内存 LRU | 单 exe 17MB，零外部依赖 |

**与本项目的差异点（检索侧）**

1. **索引 vs 无索引**：DocFetcher / Recoll 把"文本 → 词 → 文档"建成倒排表，搜索是查表（与文档数几乎无关）；本项目每次都要把每个文件的正文取出来做子串匹配，成本与"文件数 × 正文长度"线性相关。P1 那 12 秒上限就来自这里。
   - 取舍：倒排索引要维护（文件改动、删除、分词、索引损坏），体积约等于原文；对"几千份、几十 MB"的语料，无索引更快落地。**中文分词**也是坑：Recoll 默认用 n-gram，DocFetcher 靠 Lucene 的 CJK bigram。
2. **解析器依赖**：DocFetcher/Recoll/rga 都靠第三方（Tika、antiword、pandoc）。本项目的 `inflate + ZIP + CFB + BIFF8` 全自己写，**换来单文件免安装**，代价是格式覆盖窄（没有 pptx、pdf、rtf、odt、wps）且要自己扛格式变体（B4/B5/B6 都是这个代价）。
3. **缓存形态**：rga 用**一个 SQLite 库 + zstd 压缩 + 含解析器版本的 key**；本项目用**每文件一个未压缩文本文件、key 只有 path|size|mtime**。前者 IO 次数少一个数量级，而且升级解析器后会自动失效——本项目改了 `legacy_office.cpp` 之后，旧缓存还会被继续使用（**这是一个隐藏的正确性问题**：解析器修好了 bug，用户却还在读旧缓存，直到文件本身被修改）。
4. **结果呈现**：Recoll/DocFetcher 是"文档列表 + 文档内命中"，按相关度排序；本项目是"命中行平铺 + 按文件分组"，更适合"我要看这句话的上下文"的取词-搜索闭环。

## 五、建议的落地顺序

| 优先级 | 事项 | 改动量 | 收益 |
|---|---|---|---|
| P0 | B1 Tab 焦点（4 行）、B2 搜索线程读快照（10 行）、B3 取词重试上限（10 行） | 半小时 | 修掉 3 个确定性缺陷 |
| P1 | 缓存 key 加**解析器版本号**（1 行常量 + 拼进 key） | 10 分钟 | 避免"修好解析器但用户还在读旧缓存" |
| P1 | P2 锁外写盘 | 半天 | 建缓存时搜索不再卡顿 |
| P2 | P1 缓存合并成单库/单文件索引 | 2–3 天 | 万级文件从 12s → 亚秒 |
| P2 | P4 XML 扫描零拷贝 + P3 免分配匹配 | 1 天 | 大 docx/xlsx 解析 2–3 倍 |
| P3 | B4/B5/B6 格式健壮性 + B9 DPI | 1 天 | "和 Word 搜出来不一样"的投诉会明显减少 |
| P4 | 可选倒排索引（学 DocFetcher/Recoll） | 1–2 周 | 十万级文件才有必要，当前语料不需要 |
